what is the correct way to make npm packages with .node napi addons that needs static lib depending on platform? - like it requires a native lib no matter what, but it needs a diferent one depening on platform+arch, How do i do this correctly so that the published package doesnt force download bins for other platforms that it doesnt actually need?

Yes. The clean npm pattern is platform-specific optional packages, rather than putting all native libraries in the main package and trying to select one at runtime.

The important distinction is:

Your JS/N-API package is platform-independent.
The actual .node binary + static native library are platform-specific.
npm should know about that platform specificity at dependency resolution time, not just at runtime.

npm explicitly supports os, cpu, and libc constraints in package.json, and optional dependencies that don't match the current platform are skipped.

Recommended structure

Something like:

my-addon/
├── package.json
├── index.js
└── native/
    └── ...
    
my-addon-linux-x64/
├── package.json
└── my-addon.node

my-addon-linux-arm64/
├── package.json
└── my-addon.node

my-addon-darwin-x64/
├── package.json
└── my-addon.node

my-addon-darwin-arm64/
├── package.json
└── my-addon.node

my-addon-win32-x64/
├── package.json
└── my-addon.node

Then the main package has:

{
  "name": "@foo/my-addon",
  "version": "1.0.0",
  "main": "index.js",
  "optionalDependencies": {
    "@foo/my-addon-linux-x64": "1.0.0",
    "@foo/my-addon-linux-arm64": "1.0.0",
    "@foo/my-addon-darwin-x64": "1.0.0",
    "@foo/my-addon-darwin-arm64": "1.0.0",
    "@foo/my-addon-win32-x64": "1.0.0"
  }
}

And each platform package declares exactly where it is valid.

For example, @foo/my-addon-linux-x64/package.json:

{
  "name": "@foo/my-addon-linux-x64",
  "version": "1.0.0",
  "os": ["linux"],
  "cpu": ["x64"],
  "main": "my-addon.node"
}

Linux ARM64:

{
  "name": "@foo/my-addon-linux-arm64",
  "version": "1.0.0",
  "os": ["linux"],
  "cpu": ["arm64"],
  "main": "my-addon.node"
}

macOS ARM64:

{
  "name": "@foo/my-addon-darwin-arm64",
  "version": "1.0.0",
  "os": ["darwin"],
  "cpu": ["arm64"],
  "main": "my-addon.node"
}

npm then evaluates the os/cpu restrictions and doesn't install the packages that don't apply to the user's machine.

Your index.js can simply select the package:

const { platform, arch } = process;

const packages = {
  "linux-x64": "@foo/my-addon-linux-x64",
  "linux-arm64": "@foo/my-addon-linux-arm64",
  "darwin-x64": "@foo/my-addon-darwin-x64",
  "darwin-arm64": "@foo/my-addon-darwin-arm64",
  "win32-x64": "@foo/my-addon-win32-x64"
};

const name = packages[`${platform}-${arch}`];

if (!name) {
  throw new Error(`Unsupported platform: ${platform}-${arch}`);
}

module.exports = require(name);
But there's an even nicer variant

You don't necessarily need the platform packages to contain the static library separately.

If your N-API addon is:

addon.node

and you statically link:

libfoo.a

then the resulting .node already contains libfoo.a.

So your platform package can just contain:

@foo/my-addon-linux-x64/
└── addon.node

and your build system does something equivalent to:

addon.node
    └── statically linked libfoo.a

That is generally preferable if the static library is an implementation detail.

Node-API itself is ABI-stable across Node.js versions, but that doesn't automatically make the ABI of your external native libraries stable. Static linking is one way of avoiding a runtime dependency on that external library. Node's documentation specifically cautions that external libraries don't inherit N-API's ABI guarantees.

Why I would NOT do this

A tempting approach is:

{
  "optionalDependencies": {
    "my-native-linux-x64": "...",
    "my-native-linux-arm64": "...",
    "my-native-darwin-x64": "...",
    "my-native-darwin-arm64": "..."
  }
}

and then put all the binaries in those packages without os/cpu metadata.

That defeats the purpose: npm sees all of them as valid dependencies and may download/install all of them.

The crucial part is that each platform package itself declares its compatibility:

"os": ["linux"],
"cpu": ["x64"]

rather than relying on your JS code to decide which one to use.

This scales really nicely

For example, suppose you support:

Package	OS	CPU	Contains
@foo/addon-linux-x64	Linux	x64	.node + libfoo
@foo/addon-linux-arm64	Linux	arm64	.node + libfoo
@foo/addon-darwin-x64	macOS	x64	.node + libfoo
@foo/addon-darwin-arm64	macOS	arm64	.node + libfoo
@foo/addon-win32-x64	Windows	x64	.node + libfoo

Then someone on:

macOS arm64

gets approximately:

@foo/my-addon
└── @foo/my-addon-darwin-arm64
    └── my-addon.node

rather than downloading Linux, Windows, and Intel binaries.

And if you additionally have Linux glibc vs musl differences, you can use npm's libc field as well. npm documents libc specifically for this case.

For example:

{
  "name": "@foo/my-addon-linux-x64-gnu",
  "os": ["linux"],
  "cpu": ["x64"],
  "libc": ["glibc"]
}

and:

{
  "name": "@foo/my-addon-linux-x64-musl",
  "os": ["linux"],
  "cpu": ["x64"],
  "libc": ["musl"]
}
One important caveat: package managers

This pattern is particularly natural with npm, and modern package managers generally understand the os/cpu metadata. But if you care about npm + pnpm + Yarn + Bun, I'd test the resulting published package with all of them, because native-package installation behavior has historically differed between package managers.

Also test:

npm pack

and inspect the resulting tarball. You generally want the main package's tarball to contain only the JS loader/metadata, while the platform packages contain the actual native binaries.

The Node.js docs also recognize this general ecosystem pattern: tools such as prebuild and prebuildify exist specifically for distributing precompiled native addons.

In short

I'd use:

@foo/addon
    │
    ├── optionalDependency → @foo/addon-linux-x64
    ├── optionalDependency → @foo/addon-linux-arm64
    ├── optionalDependency → @foo/addon-darwin-x64
    ├── optionalDependency → @foo/addon-darwin-arm64
    └── optionalDependency → @foo/addon-win32-x64

with os + cpu on every platform package, and statically link the appropriate native library into each .node.

That gives you one public package users install, while npm does the platform filtering and only fetches the native artifact applicable to their machine.

Is that kind of stuff just built into optional deps or? because if i run bun add @foo/addon or npm i @foo/addon i expect the import to be import { foo } form "@foo/addon" - and under the hood it already knows which native to fetch and actually fetches it. no matter the platform

Exactly — that behavior is something you build into the package's dependency graph, not something import itself does.

The key is:

"optionalDependencies": {
  "@foo/addon-linux-x64": "1.0.0",
  "@foo/addon-linux-arm64": "1.0.0",
  ...
}

combined with each package's os/cpu constraints.

So when the user runs:

npm install @foo/addon

npm sees:

@foo/addon
  ├─ optional → @foo/addon-linux-x64     [os=linux,cpu=x64]
  ├─ optional → @foo/addon-linux-arm64   [os=linux,cpu=arm64]
  ├─ optional → @foo/addon-darwin-x64    [os=darwin,cpu=x64]
  └─ optional → @foo/addon-darwin-arm64  [os=darwin,cpu=arm64]

It evaluates the package constraints while resolving/installing dependencies.

On an M-series Mac:

@foo/addon
└── @foo/addon-darwin-arm64    ← installed

The others are skipped.

On Linux x64:

@foo/addon
└── @foo/addon-linux-x64        ← installed

So yes: the package manager does the fetching and filtering.

Then your public API stays completely normal

Your published @foo/addon contains something like:

const native = require(
  `@foo/addon-${process.platform}-${process.arch}`
);

module.exports = native;

So the user writes exactly:

import { foo } from "@foo/addon";

They don't know or care that another package was installed.

Why optionalDependencies?

This is the important bit.

If these were ordinary dependencies:

"dependencies": {
  "@foo/addon-linux-x64": "1.0.0",
  "@foo/addon-linux-arm64": "1.0.0",
  "@foo/addon-darwin-arm64": "1.0.0"
}

the package manager would generally need to install all of them.

But with:

"optionalDependencies": {
  "@foo/addon-linux-x64": "1.0.0",
  ...
}

plus:

{
  "os": ["linux"],
  "cpu": ["x64"]
}

on the platform package, the package manager can say:

"This optional dependency isn't compatible with this platform, so don't install it."

That's precisely the mechanism you're looking for.

There's one subtle point

optionalDependencies by itself doesn't mean "pick the correct platform package."

It means roughly:

"Try to install these dependencies, but failure/incompatibility shouldn't make the whole package installation fail."

The os / cpu / libc metadata is what makes the individual packages platform-selective.

So the combination is:

optionalDependencies
        +
   os / cpu / libc
        ↓
platform-specific installation

This is the same general architecture used by many modern native Node packages.

You can make the loader even cleaner

Instead of:

require(`@foo/addon-${process.platform}-${process.arch}`)

you can have:

const bindings = require(`@foo/addon-${process.platform}-${process.arch}`);

export const { foo } = bindings;

Or, if you want the native package completely hidden:

// @foo/addon/index.js

module.exports = require(
  `@foo/addon-${process.platform}-${process.arch}`
);

Then consumers see only:

import { foo } from "@foo/addon";

while the actual dependency tree looks different depending on the machine.
